# deep-research

> 通过多源互联网数据对任意主题进行结构化深度调研，产出有据可查的分析结论。覆盖社区论坛、代码仓库、学术搜索、问答平台、新闻、技术出版物、金融行情等数据源（按可用性分四级：直连可用 / 量化专用 / 限流需key / 需代理）。

---

## 适用场景

| 触发条件 | 说明 |
|---------|------|
| "调研一下 XX"/"查查 XX 方面的资料" | 任何需要从公开网络收集证据的主题 |
| "验证 XX 是否成立" | 需要多来源交叉验证的假设 |
| "分析 XX 的现状和趋势" | 需要对某领域做全景式梳理 |
| "帮我搜一下 XX 相关的信息" | 用户指定搜索方向，需要结构化输出 |
| "评估/验证某策略是否有效" | 金融量化策略实证（先拉指数K线做对比，再补学术/社区证据） |

| 不适用 | 原因 |
|--------|------|
| 纯内部数据调研（公司报表、用户日志等） | 本技能仅覆盖公开网络数据 |
| 需付费数据库（Gartner / Forrester 报告 / CSMAR / Wind） | 仅使用免费可公开访问的 API 和站点 |
| 用户要求直接给结论不要证据 | 本技能核心价值是"有据可查" |

## 执行步骤

### 1. 明确调研框架

```
1. 确定调研主题和核心问题
2. 确定调研维度（根据主题类型选择）：
   - 事实型：XX 是什么？谁在做？核心概念？
   - 验证型：假设 X 是否成立？证据在哪？
   - 全景型：XX 领域的格局、玩家、趋势
   - 技术型：XX 技术有哪些方案？对比优劣？
   - 趋势型：XX 方向近 1~3 年的变化
   - 金融/策略验证型：策略因子是否有效？市场实证 + 学术 + 社区证据
3. 确定核心搜索词（3~6 个，覆盖不同角度）
4. 确定数据源优先级（按主题类型）：
   - 金融/量化主题 → 优先直连可用的指数K线实证（腾讯行情/中证指数），再补学术（arXiv/NBER）与社区（雪球/聚宽）
   - 需代理的源（Wikipedia/HF/SSRN）默认降级，不阻塞主流程
```

### 2. 数据源选择与预检

#### 2.1 完整数据源目录（分级）

**一级：直连可用（优先使用）**；**二级：限流/需 key**；**三级：需代理**；**已移除**的源不再尝试。

> **⚠️ 判定要点**：Wikipedia / Hugging Face / SSRN / NewsAPI 国内直连不通，属**需代理**而非源失效——预检超时时先判这一条，再决定是否降级。
>
> **兜底源（最后手段）**：免费源与页面解析均无结果、或目标站反爬封禁时，调用 `deepseek-web-search` 技能的 `search`（结构化结果带 `authority` / `rerank_score`，可参与证据分级），抓正文用其 `fetch`。
> 该源需 `DEEPSEEK_API_KEY` 且按次计费（5 元 / 1000 次），**只在前面各源全部失效后启用**，且在报告中标注「兜底源获取」。
>
> 完整分级目录（含测速、备注、已移除源说明）见 `refs/data-sources.md`
#### 2.2 按调研类型推荐数据源组合

```
┌─────────────────┬─────────────────────────────────────────────────┐
│  调研类型        │  推荐数据源组合（优先级排序）                       │
├─────────────────┼─────────────────────────────────────────────────┤
│  产品/市场验证    │ HN → Product Hunt → GitHub → Reddit → NewsAPI   │
│  技术选型对比    │ Stack Overflow → GitHub → HN → arXiv → Dev.to   │
│  学术前沿追踪    │ arXiv → Semantic Scholar → HF → GitHub          │
│  趋势/行业分析   │ HN → NewsAPI → GNews → Reddit → Lobste.rs       │
│  开源生态评估    │ GitHub → PyPI/npm → HF → Stack Overflow         │
│  事实核查        │ Wikipedia(需代理) → arXiv → Semantic Scholar     │
│  ML/AI 领域调研  │ HF(需代理) → arXiv → GitHub → PapersWithCode    │
│  金融/量化策略    │ 腾讯行情/中证指数(实证) → NBER → arXiv → 雪球/聚宽│
│  策略有效性验证  │ 指数长周期K线对比 → 学术论文 → 社区讨论 → 开源项目 │
│  中文知识/概念    │ 百度百科 → 知乎 → 简书 → 搜索引擎快照            │
│  中文软件技术    │ CSDN → 博客园 → 掘金 → SegmentFault → OSCHINA → InfoQ │
│  国内开源生态    │ Gitee → OSCHINA → GitHub(镜像) → 掘金            │
└─────────────────┴─────────────────────────────────────────────────┘
```

> 表中「搜索引擎快照」指 `deepseek-web-search` 的 search / fetch——它是计费兜底源，启用条件见 §2.1「兜底源」。

#### 2.3 预检命令

每条源一行探测命令（curl / python），命中 2xx 即视为可用，随后按下方判据定级。

> 各源预检命令见 `refs/data-sources.md` →「预检命令」
> **预检判定规则**：
> - `200` 且返回正常内容 → 可用
> - `403` / `429` → 源有效但**限流**，降级到替代源（如 GitHub → 官网/搜索引擎）
> - 超时/无法连接 → 先确认**是否需科学上网**（Wikipedia/HF/SSRN/NewsAPI），再判定源是否失效
> - 预检前先按本表探测，**不要把"需代理"误判为"源失效"**

### 3. 多维度数据采集

#### 3.1 搜索词设计

```
原则：同一主题从 5 个不同角度出搜索词

角度 1：核心概念   → {主题名} {核心术语}
角度 2：问题/痛点   → challenge / problem / limitation + {领域}
角度 3：方案/项目   → {具体方案/项目名}
角度 4：对比/评价   → vs / comparison / alternative / pros cons
角度 5：时间趋势   → recent / 2025 / state of the art + {主题}

每个类型调研选择 3~4 个角度，生成 3~6 个搜索词。
```

#### 3.2 搜索词模板（按调研类型）

```python
# 技术选型型
["{技术A} vs {技术B}", "{技术} benchmark", "{技术} pros cons",
 "{技术} architecture", "alternatives to {技术}"]

# 趋势判断型
["{领域} trends", "{领域} state of the art", "HN: Show HN {领域}",
 "{领域} 2025 2026"]

# 事实核查型
["{概念} definition", "{概念} Wikipedia", "{概念} overview",
 "{概念} example tutorial"]

# 产品格局型
["{领域} comparison", "{领域} landscape", "{代表产品} alternatives",
 "open source {领域}", "best {领域}"]

# 痛点验证型
["why {领域} is hard", "{领域} problem frustration",
 "{现有方案} sucks", "HN: {领域} pain point"]

# ML/AI 模型调研
["{任务类型} model benchmark", "SOTA {任务类型}",
 "huggingface {任务类型}", "best {任务类型} model"]

# 金融/策略有效性型（A 股）
["{策略名} 有效性", "{因子} A股 实证", "{因子} premium China",
 "{因子} anomaly", "{指数产品名} 业绩", "{因子} backtest A-share"]

# 中文知识/概念型
["{概念} 是什么", "{概念} 百科", "{概念} 知乎", "{概念} 详解"]

# 中文软件技术型
["{技术} 教程", "{技术} 实战", "{技术} 原理 CSDN", "{技术} 踩坑",
 "{技术} 对比 掘金", "{技术} 最佳实践 博客园"]
```

#### 3.3 简易 API 调用示例（通用版）

三源并行采集模板：并发发起 → 任一成功即采用 → 全部失败再降级下一源；**降级链的终点**是 §2.1 的兜底源 `deepseek-web-search`（计费，仅此一处启用）。每个源的字段映射（`title`/`points`/`date`/`text`）与超时、重试参数在示例中给定，直接照抄改 query。

> 完整并发模板（HN / GitHub / arXiv 三源 + 统一字段）见 `refs/collection-examples.md` →「三源并行采集」
#### 3.3.1 中文源采集示例（页面解析）

> 中文源多无公开 JSON API，统一走页面解析。核心：带 UA 抓 HTML → 用 BeautifulSoup/正则提取标题与正文。反爬严时改走 `deepseek-web-search` 的 `fetch` 取正文（其服务端抓取，绕过本地反爬）。

> 完整示例见 `refs/collection-examples.md` →「中文源页面解析」
#### 3.4 金融/量化采集示例（腾讯行情）

腾讯行情是公开 JSON 接口（`web.ifzq.gtimg.cn`），**直连可用、无需 key**；`urllib` + `User-Agent` 头即可，前复权用 `qfq`，日 K 约 2000 根（≈8 年），更长历史取 `week`。

> 完整采集函数（K 线 + 收盘序列 + 累计/年化收益计算）见 `refs/collection-examples.md` →「腾讯行情 K 线」
### 4. 数据解析与结构化

每个数据源提取统一的结构化字段，便于后续交叉对比：

```python
# 统一接口：每条证据的结构
{
    "source": "数据源简称",       # hn / github / stackoverflow / wikipedia / arxiv / reddit / devto / huggingface / producthunt / newsapi
    "source_id": "在该源中的唯一标识",
    "title": "标题",
    "url": "原文链接",
    "snippet": "摘要/前 500 字符",   # 原始引文片段
    "date": "发布日期",
    "score": 数值指标,              # points/stars/votes/downloads 统一归一化为 0~100
    "tags": ["标签"],               # 关键词/分类
    "metadata": {                   # 数据源特有字段
        "source_api": "API 端点",
        "language": "主要语言",
        "author": "作者/发布者",
        "type": "讨论/项目/文章/论文/新闻"
    }
}
```

**注意事项：**
- 每个数据点标注 `source + source_id` 双重标识，确保可回溯到原文
- snippet 字段保留原文前 500 字符作为直接证据，不做 paraphrasing
- 标记 `date`，过期数据（>2 年）在分析时标为"历史参考"
- score 跨源归一化：Stars / Points / Votes 各自映射到 0~100 区间
- 区分 **事实**（有明确来源的陈述）vs **观点**（个人评价、社区讨论）

### 5. 交叉验证与结构化分析

#### 5.1 三层验证

```
层次 1：信源三角
  ≥2 个独立来源一致 → 置信度高
  仅 1 个来源      → 置信度低，可能是噪音
  来源间矛盾        → 记录矛盾，分析原因（立场差异？时效差异？）

层次 2：时效性
  近 1 年  → 当前有效
  1~3 年   → 可能已变化，标注参考时间
  >3 年    → 历史参考，不可用于当前决策

层次 3：上下文与偏见
  检查原文上下文（不只是标题/摘要）
  标注数据源固有偏见：
    - HN: 偏技术早期采用者, 硅谷视角
    - Reddit: 偏社区情绪, 可能放大负面
    - Product Hunt: 发布即巅峰, 长期数据少
    - GitHub: Star 数量不等于活跃度/质量
    - Stack Overflow: 偏传统技术栈
```

#### 5.2 证据分级表输出格式

```markdown
| # | 发现 | 来源 | 置信度 | 时效 | 证据强度 |
|---|------|------|--------|------|---------|
| 1 | {发现陈述} | HN #12345 + GitHub A/B | ★★★ | 2025 | 多源一致 |
| 2 | {发现陈述} | SO #67890 | ★★☆ | 2024 | 单源高票 |
| 3 | {发现陈述} | Reddit 帖子 | ★☆☆ | 2023 | 单源低分 |
```

**证据强度定义：**

| 强度 | 含义 | 示例 |
|------|------|------|
| ★★★ 多源一致 | ≥2 个独立来源指向同一结论 | HN 讨论 + GitHub 项目趋势一致 |
| ★★☆ 单源高质 | 1 个高质量来源（高票/高星/权威） | Stack Overflow 高赞回答 |
| ★☆☆ 单源参考 | 1 个低质量来源或观点 | Reddit 个例抱怨 |
| ⚠️ 存在矛盾 | 不同来源结论相反 | 需要进一步分析 |

### 6. 综合分析与结论输出

将采集和分析结果组织为输出文档：

```markdown
# 调研报告：{主题}

## 1. 调研框架
- 核心问题
- 调研维度
- 数据源清单（实际使用的源 + 未用到的计划源及原因）
- 搜索词列表

## 2. 核心发现

### 2.1 事实性发现
{事实层面的关键发现，附证据来源}

### 2.2 观点与趋势
{观点层面的发现，区分不同来源的立场差异}

### 2.3 矛盾与缺口
{不同来源的矛盾点，或信息不足以覆盖的缺口}

## 3. 证据清单
{按证据强度排列的表格}

## 4. 结论
{基于证据的结论，每条标注置信度}

## 5. 待补充
{需要进一步调研的方向、建议补充的数据源}
```

**输出原则：**
- **先结论，再证据**：每个小节先说结论，再给证据
- **置信度标注**：每条结论标注（确定/待验证/待补充）
- **保留原始引文**：关键结论附上原文截取（snippet），不 paraphrasing
- **不做推测**：证据不足时说"待补充"，不用假设填充
- **声明未用源**：计划但实际未使用的数据源要注明原因（rate limit / 无相关数据）

## 常见错误

| 问题 | 现象 | 处理 |
|------|------|------|
| API rate limit | GitHub 403 / Semantic Scholar 429 | 降级到替代源（GitHub→官网；S2→arXiv），降低请求频率，必要时申请 token |
| 搜索结果不相关 | 返回大量无关结果 | 优化搜索词：加限定词、精确短语、技术关键词 |
| 数据过旧 | 搜到 2~5 年前的结果 | API 参数过滤 created_at，优先近 1 年 |
| 高估项目热度 | Star 高但已弃坑 | 检查 last_push / pushed_at，弃坑标为历史 |
| 来源偏见 | 某个来源偏袒某方 | 标注来源立场，寻找对立观点 |
| 证据不足强行结论 | 结论无数据支撑 | 标注低置信度，写"待补充" |
| 混淆事实与观点 | 把帖子观点当事实引用 | 每段证据标注是"事实"还是"观点" |
| 单一来源依赖 | 仅靠 HN 或仅靠 GitHub | ≥2 个独立来源交叉验证 |
| **把"需代理"当"源失效"** | Wikipedia/HF/SSRN 超时误判为失效 | 先开科学上网再测；报告须标注"因网络限制未用" |
| **把"限流"当"源失效"** | GitHub 403 / S2 429 误删源 | 区分限流与失效：限流源保留并在报告中降级 |
| 金融调研只用社区源 | 无实证数据支撑结论 | 量化主题先拉指数K线/官方业绩做实证，再补学术与社区证据 |
| **免费源全部无结果** | 各源 0 条命中或反爬封禁，调研卡住 | 走 §2.1 兜底源 `deepseek-web-search`（计费），报告标注获取途径 |
