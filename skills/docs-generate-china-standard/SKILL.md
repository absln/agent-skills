# 文档编写

> 按 GJB 438C 格式编写**项目验收/合规性文档**——这是面向评审与交付的正式文档，区别于开发阶段的技术制品。
> 
> **触发边界**：仅当用户明确要求"按 GJB 格式输出""准备验收文档""编写合规性文档"等时启用。开发过程中产生的需求规格、数据模型、设计说明、任务计划是**开发指导物**，由 `task-manager`、`database-standards` 等技能产出，不属于本技能范围。

---

## 适用场景

| 触发条件（明确要求 GJB 格式） | 说明 |
|---------|------|
| 用户要求"按 GJB 438C 编写{文档类型}" | 自动匹配文档类型与模板 |
| 项目验收交付，需要成套合规性文档 | 按生命周期阶段批量生成 |
| 对已有 GJB 文档进行审阅/质量检查 | 对照本技能「阶段四：审阅」自检清单逐项检查 |

| **不触发**（开发制品，不由本技能负责） | 替代技能 |
|--------|------|
| 编写开发用的需求规格（`docs/需求/`） | `task-manager` — 阶段一产出 |
| 设计数据库 Schema（`docs/设计/` JSONC） | `database-standards` |
| 编写模块设计说明（`docs/设计/`） | `task-manager` + 编码阶段 |
| 制定开发任务计划（MCP tasks 表） | `task-manager` — 规划阶段 |
| 非 GJB 格式的轻量文档（README/CHANGELOG） | 无对应模板，自由撰写 |

## 执行步骤

### 阶段一：收集

1. **确定文档类型**：根据用户任务匹配上表中的文档标识（SDP/SRS/SDD/...），如无法确定则列出候选请用户选择。
3. **加载模板**：打开本技能 `templates/{标识}-{名称}-模板.md`，以模板结构作为骨架。
4. **扫描参考资料**：扫描 `docs/refs/` 目录，收集与任务相关的需求、设计、接口等参考文档。
5. **解析非 Markdown 资料**：对 docx/pptx/xlsx/pdf/图片等格式的参考资料，调用 `file-parser` 技能提取文本。
6. **分析信息缺口**：对照模板骨架和参考资料，识别缺失的关键信息，列出清单主动咨询用户。**禁止在信息不全时编造数据。**

### 阶段二：规划

1. **确定文档深度**：判断输出概要级还是详细级（依据对应模板中标注的概要级/详细级骨架）。
2. **结构化大纲**：列出目标读者、适用范围、必要章节，标明哪些有资料支撑、哪些待确认。
3. **证据映射**：每个结论需对应到参考资料的来源位置（如"引自《XXX 设计说明书》§3.2"）。

### 阶段三：撰写

1. **模板为准**：以本技能 `templates/` 中模板结构为核心，结合参考资料填充具体内容。
2. **标注不确定性**：信息不足处写"**待确认**"或"**待补充**"，禁止用假设替代。
3. **术语统一**：首次出现的术语给出全称或定义；全文档名称一致。
4. **格式规范**：
    - Markdown 格式，标题从 `#` 开始
    - 章节数字编号：`# ` → `## ` → `### `
    - 关键流程用编号步骤，复杂关系用表格
    - 架构图使用 ASCII art 或 Mermaid 语法
5. **输出到 `docs/draft/`**：文件命名 `{文档标识}_{文档名称}_{日期}.md`（如 `SRS_软件需求规格说明_2026-07-31.md`）。

### 阶段四：审阅

1. **逐项自检**：
    - [ ] 结构完整：章节不缺，编号不跳
    - [ ] 目标明确：读者知道这份文档解决什么问题
    - [ ] 方案具体：不是概述，有具体设计内容
    - [ ] 术语统一：同一概念全文档名称一致
    - [ ] 边界清楚：明确写了"不做什么"或"不在范围内"
    - [ ] 异常覆盖：不仅写了正常流程，也写了异常处理
    - [ ] 风险标注："待确认/待补充"项已明确标出
    - [ ] 可直接用：后续开发/测试/评审能直接参考
2. **质量度量**：按本技能末尾「质量度量速查」量化指标逐项计算并记录。
3. **参考文档冲突处理**：若参考文档间存在矛盾，以最新版本为准，并在文档中标注差异。

## 核心原则（速查）

| 原则 | 含义 |
|------|------|
| 以资料为证据 | 所有结论必须建立在参考文档之上 |
| 不确定就标注 | 信息不足写"待确认"，禁止假设填充 |
| 结论先行 | 先结论后分析，先方案后依据 |
| 禁止空泛评价 | 不得出现"性能良好""扩展性强"等无依据表述 |
| 禁止编造数据 | 信息不全时先咨询用户，不得自行编造 |
| 面向交付 | 文档能直接用于评审、开发、测试 |

## 常见错误

| 错误 | 正确做法 |
|------|---------|
| 没读模板就写，结构跑偏 | 先打开本技能 `templates/` 对应模板，以模板为骨架 |
| 编造业务规则/技术参数 | 缺信息标注"待确认"，咨询用户后补上 |
| 只有概述没有具体方案 | 用表格、编号步骤、数据定义替代空洞描述 |
| "性能良好""可扩展性强"等空话 | 给出具体指标："支持 1000 QPS""水平扩展至 5 节点" |
| 全文 A 处叫"用户表"B 处叫"USER 表" | 首次定义术语后全文档统一 |
| 只写正常流程不写异常处理 | 每个功能至少覆盖：超时、无权限、数据不存在、并发冲突 |
| 参考文档冲突时自行判断取舍 | 标注差异，以最新版本为准 |
| 输出位置错误 | 文档写入 `docs/draft/`，不写入 `.agents/` 或 `docs/refs/` |

## 追踪机制

格式：`WRITE-{序号}.{子任务}.{执行点}`

```
WRITE-001         任务     SRS-软件需求规格说明     ✅ 完成
WRITE-001.1       子任务   需求收集                  ✅ 完成 (3份参考文档)
WRITE-001.1.1     执行点   模板加载                  ✅ SRS-软件需求规格说明-模板.md
WRITE-001.1.2     执行点   参考资料解析              ✅ (2 docx, 1 pdf)
WRITE-001.2       子任务   功能需求撰写              ✅ (12个功能点)
WRITE-001.3       子任务   审阅与质检                ⚠️ 3项待确认, 2项待补充
```

状态：✅ 完成 | ⚠️ 部分完成 | ❌ 失败 | ⏳ 待执行 | 🔄 进行中

|------|------|---------|
