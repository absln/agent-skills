# skill-creator

将项目经验、技术决策、重复性工作模式提炼为可复用的标准技能文件，实现 Agent 自创建、自演进。

---

## 适用场景

| 触发用户指令 | 说明 |
|-------------|------|
| "归纳一下"/"总结一下" | 用户完成某任务后要求提炼经验 |
| "总结经验"/"记下来" | 用户识别到可复用的工作模式 |
| "把这个写成技能" | 用户明确要求将当前过程技能化 |
| 重复 3 次以上的操作 | Agent 自行识别到重复模式，主动建议技能化 |

| 不适用 | 原因 |
|--------|------|
| 一次性操作无复用价值 | 技能化的投入产出比低 |
| 设计文档产出 | 归入 `docs/` 而非技能 |
| 修改已有技能已有覆盖 | 应更新现有技能，不新建 |

---

## 执行步骤

### Step 1：需求定义（先不写文件）

回答 4 个问题，确定技能边界：

```
Q1 — 什么时候触发这个 Skill？
    → 决定 description 怎么写（最关键）
    → 例："当需要添加后端 CRUD 接口时"

Q2 — 输入是什么？
    → 用户/Agent 提供哪些信息
    → 例："数据表名、字段定义"

Q3 — 输出强制格式是什么？
    → Markdown / JSON / 固定模板
    → 例："标准 SKILL.md（frontmatter + 正文）"

Q4 — 执行步骤顺序、校验规则、边界约束是什么？
    → 步骤 5±2 个，合并同类操作
    → 校验规则：什么算完成？
```

> 如果 4 个问题中任一个回答模糊 → 补充信息后再继续。
> ❌ 坏示例：数据分析+写周报+绘图（职责混杂）
> ✅ 好示例：结构化周报生成 Skill

---

### Step 2：创建目录结构

```
{技能根目录}/{skill-name}/          # kebab-case，与 name 一致

# 技能根目录按宿主约定取：
#   本仓库            skills/            （唯一事实源，dist 构建与 npx 分发都读它）
#   其他宿主项目      .agents/skills/    （部分客户端约定）
# 下文一律简写为 {技能根目录}/，不要照抄某一种。
├── SKILL.md                     # 【必须】frontmatter + 执行指令
├── scripts/                     # 可选：可执行脚本（py/sh/ts）
├── refs/                  # 可选：规范、文档、样例
└── assets/                      # 可选：模板文件
```

> 大段参考资料移入 `refs/`，正文只写指引，控制 SKILL.md 长度。
> **主文件 ≤500 行**（含 frontmatter）：超出的部分外移到 `refs/`，但正文必须留「约束摘要 + 链接」，不能只剩一句「详见 xxx」。

---

### Step 3：编写 SKILL.md

#### 3.1 先写 YAML Frontmatter（必须）

```yaml
---
name: {skill-name}             # 必填；小写 kebab-case，与目录名一致；≤64 字符
description: {一句话触发场景}    # 必填；≤1024 字符；决定 Agent 何时自动加载
---
```

> ⚠️ **description 决定 Agent 能否自动识别并加载该技能！写得模糊=永远不会触发。**
> 格式：`{做什么}；当{什么场景}时自动启用。`
> 例：`在 {后端技术栈} 后端实现标准 CRUD 功能；当需要添加后端接口或数据表时自动启用。`
>
> 频繁误触发 → **收紧 description**
> 一直不触发 → **扩充 description 场景描述**

#### 3.1.1 规范依据（Anthropic Agent Skills）

`SKILL.md` = **YAML frontmatter + Markdown 正文**，遵循 Agent Skills 规范：

| 字段 | 要求 |
|---|---|
| `name` | 必填；≤64 字符；仅小写字母、数字、连字符；与目录名一致 |
| `description` | 必填；**≤1024 字符**；模型判断「是否加载本技能」的**唯一依据** |
| `license` / `allowed-tools` / `metadata` | 可选，按需添加 |

**渐进披露三层**（写作时按这个分层，不要把内容堆在 description 里）：

| 层 | 内容 | 何时进入上下文 |
|---|---|---|
| ① 索引 | `name` + `description` | **常驻**（系统提示的技能清单） |
| ② 正文 | `SKILL.md` 的 Markdown 部分 | 技能命中时才读 |
| ③ 附属文件 | `refs/` `scripts/` `assets/` | 执行中按需读，**不进入索引** |

> 因为 ① 常驻，`description` 必须同时回答「做什么」和「什么时候用」，但**不要写成正文**——正文放 ②。
> ③ 里的文件不要重复列进索引：正文用**相对路径**（如 `详见 refs/<规则名>.md`）指路即可。

#### 3.2 流程型技能模板（Process）

> 适用：有明确的 **输入→步骤→产出** 流程。如 `task-execution`、`document-gjb-writing`。

```markdown
# {skill-name}

> {一句话描述技能用途}

---

## 适用场景

| 触发条件 | 说明 |
|---------|------|
| {场景1} | {说明} |
| {场景2} | {说明} |

| 不适用 | 原因 |
|--------|------|
| {边界1} | {说明} |

---

## 执行步骤

### 1. {步骤名}

```
{步骤指令，每行一条}
```

### 2. {步骤名}

```
{步骤指令}
```

...（3~7 步）

---

## 常见错误

| 问题 | 现象 | 处理 |
|------|------|------|
| {错误} | {现象} | {处理方式} |

---

## 输出

```
{执行后生成的文件路径清单}
```
```

#### 3.3 规范型技能模板（Standards）

> 适用：定义规则、约束、标准，**无执行步骤**，触发后全文加载作为参考。如 `database-standards`、`backend-rust-standards`。

```markdown
# {skill-name}

> {一句话描述规范范围}

---

## 1. 核心原则

{3~5 条设计原则，简述核心理念}

---

## 2. {规范维度1，如：命名规范}

{具体规则，优先用表格}

---

## 3. {规范维度2，如：类型系统}

{具体规则}

---

## N. 质量门槛

- [ ] {自检项1}
- [ ] {自检项2}

---

## N+1. 禁止事项

| 禁止 | 说明 |
|------|------|
| {禁止项1} | {说明} |
```

**规范型技能的标识**：
- 无「适用场景」表 → 由 description 决定触发
- 无「执行步骤」 → 加载后作为约束全文参考
- 无「常见错误」 → 合并到禁止事项
- 结构按规范主题组织，编号章节，无步骤编号

---

### Step 4：补充附属资源（按需）

| 资源 | 位置 | 用途 |
|------|------|------|
| 业务规范/约束 | `refs/<规则名>.md` | 大段约束文档，正文只写"详见 refs/<规则名>.md" |
| 自动化脚本 | `scripts/{action}.py` | Agent 可调用的可执行脚本 |
| 输出模板 | `assets/template.md` | 固定格式的输出模板 |

> 原则：**正文只写流程指引，大块参考内容外置**，避免 SKILL.md 过长占用 token。
> 附属文件**不进入技能索引**（索引只含 `name` + `description`），所以正文必须用**相对路径**指明位置（如 `详见 refs/<规则名>.md`、`执行 scripts/<检查脚本>.py`）。

---

### Step 5：加载与测试

创建完成后，验证技能是否能正确触发和执行：

#### 5.1 两种调用方式

| 方式 | 说明 |
|------|------|
| **自动触发** | 发送匹配 description 的指令，观察 Agent 是否自动加载 |
| **强制调用** | 对话输入 `/skill:{skill-name}` 手动加载 |

#### 5.2 测试要点

| 测试类型 | 检查项 |
|----------|--------|
| **正常场景** | 能否自动启用？输出格式是否符合规范？ |
| **边界场景** | 输入残缺时如何处理？至少覆盖空输入、极值、超长输入 |
| **负向测试** | 无关任务会不会错误加载本 Skill？ |

#### 5.3 调优方法

| 现象 | 处理 |
|------|------|
| 频繁误触发 | 收紧 description：减少通用词，增加特定场景限定 |
| 一直不触发 | 扩充 description：增加更多触发场景描述 |
| 执行结果不稳定 | 在正文增加检查清单、强制规则、编号步骤 |
| 上下文过长 | 把大段参考资料移入 `refs/`，正文只写"详见..." |

---

### Step 6：迭代优化（演进）

当新经验可补充已有技能时：

```
1. 读取 {技能根目录}/{skill-name}/SKILL.md
2. 对照当前经验，检查需要变更的部分：
   - description 是否需要扩充/收紧
   - 适用场景新增/修正
   - 执行步骤补充或优化
   - 常见错误追加
3. 用 edit 工具进行精确修改
```

---

### Step 7：通知用户

```
1. 告知用户已创建/更新的技能：
   "已创建技能 {skill-name}：{一句话描述}"
   或 "已更新技能 {skill-name}：补充了 XX 错误处理"

2. 说明触发方式：
   "后续遇到同类任务时我会自动调用此技能"
```

## 常见错误

| 问题 | 现象 | 处理 |
|------|------|------|
| 名称冲突 | 新技能与已有技能处理同一问题 | 改为更新现有技能（Step 6），不新建 |
| 步骤太具体 | 技能中混入当前项目的业务细节 | 剥离为通用流程，业务细节归入 `docs/specs/` |
| 格式不全 | 缺少适用场景或常见错误 | 对照模板逐项检查 |
| 过度技能化 | 把一次性的简单操作也创建技能 | 判断标准：该操作是否可能被复用 ≥2 次 |
| 目录名含中文 | 工具链报路径错误 | 统一使用英文 kebab-case |
| description 太宽泛 | 经常在不该触发时加载 | 收紧：加限定词、减少通用场景 |
| description 太窄 | 相关任务来了却不触发 | 扩充：增加更多触发指令示例 |
