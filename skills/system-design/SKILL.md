# system-design

> 系统设计阶段编排，贯穿「需求 → 分析 → 设计 → 开发」四阶段。两条主线：**可追溯性**（每一份下游文档回指上游，每一步产出经门禁确认才进下一步）与**够用即止**（产出「决策 + 依据 + 验收标准」，不套完整模板、不写面子章节）。每步经用户确认才进下一步。
>
> 提炼自实际项目的设计实践——常见硬伤是「文档扎实但追溯断链、评审缺失、任务只有骨架」，本技能就是针对这三点的门禁设计。

---

## 适用场景

| 触发条件 | 说明 |
|---------|------|
| 启动一个新产品/新功能的设计 | 从想法到可编码任务清单 |
| 需求/分析/设计任一阶段 | 明确该阶段「产出什么、门禁是什么」 |
| 排查研发流程断链 | 需求未编号、设计不回指、评审缺失、任务只有骨架 |

| 不适用 | 原因 |
|--------|------|
| 编码/测试/集成/部署 | 用 `system-development` 技能 |
| UI 原型（骨架线框/高保真 HTML） | 用 `system-ui-design` 技能（设计阶段的 UI 切面） |
| 军方结案合规文档 | 用 `docs-generate-china-standard` 技能 |

> 本技能与 `system-ui-design` 是「主线 vs 切面」的关系：本技能规定各阶段的产出物、门禁与追溯规则；UI 原型的做法在 `system-ui-design`。

---

## 1. 四阶段总览

| 阶段 | 产出物 | 门禁（进入下一阶段前必须满足） |
|------|--------|------------------------------|
| 需求 | 功能/需求清单（编号 + 验收标准） | 需求评审 confirmed |
| 分析 | 功能清单 / 需求追踪矩阵（RTM） | 需求→功能映射完整 |
| 设计 | 概要设计 + 详细设计（数据模型/接口/流程/图/UI 原型） | 设计回指需求，字段级无矛盾 |
| 开发 | 任务清单 + 代码 + 测试 | 任务可独立执行、可验证（交 system-development） |

---

## 2. 五条铁律（实战踩过的坑）

> 违背任一条即不合格，是流程层面的「红线」。

### 铁律 1：需求必须编号，设计必须回指（可追溯性）

需求/功能清单里的每条需求/功能点**必须有唯一编号**（如 `REQ-01`、`FR-02`），不能只写自然语言段落。

详细设计每个模块/表/接口前必须标注 `源需求：REQ-xx`，形成需求追踪矩阵（RTM）：

```
| 需求 ID | 需求 | 设计模块 | 表/接口 | 状态 |
|---------|------|---------|---------|------|
| REQ-01 | 设备调度 | 任务与调度服务 | schedule_plan / POST /api/v1/schedules | 已覆盖 |
```

**为什么**：无编号 = 无法回答「需求 §3.3 对应哪张表哪个接口」，变更时无法做影响面分析。

### 铁律 2：需求必须评审确认，不能 draft 直接进设计

需求/功能条目在问题系统里**必须走 `draft → review → confirmed`**，确认后才进设计。

**为什么**：设计建立在未经确认的需求之上，一旦需求变动，设计全部返工。

### 铁律 3：任务跟踪要有血肉，不能只有骨架

任务清单必须满足：
- 覆盖**全阶段**：需求/分析/设计/编码/测试都有对应任务，不能只到设计就停；
- 每条任务有**排期**、**优先级**与**前置依赖**；
- 状态**真实流转**，不是全部停在「进行中」。

**为什么**：只记几条设计任务、全部进行中、无排期无依赖，构不成真正的跟踪体系。

> 拆出的任务**够不够格**由本铁律判断；任务**怎么写进系统**（字段名、状态值域、登记与流转操作、调用失败的兜底）一律归 `task-manager`，本技能不重复定义。

### 铁律 4：阶段边界清晰，概要设计只到「约定层」

概要设计只做**规范约定**（模块边界、职责、依赖、接口「能力+语义」、数据「实体+关系」），**不写字段级实现**。

| 对象 | 概要层（约定） | 详细设计（落地） |
|------|--------------|----------------|
| 接口 | 能力 + 输入输出语义 | 字段名/类型/HTTP 方法/状态码 |
| 数据模型 | 实体 + 关系 + 主键概念 | 建表 DDL、字段类型、索引 |
| 流程 | 步骤级（谁调用谁） | 时序图、消息参数 |
| UI | 骨架线框（区块 + 字段占位） | 高保真 HTML（字段/枚举/交互取自契约） |

**为什么**：概要设计一旦写了字段级实现，后期返工；收敛到约定层后，详细设计各文档才能各司其职。

### 铁律 5：待确认项集中管理，不散落

各文档末尾的「待确认事项」**必须汇总到一处**（一个汇总清单 + 挂到任务 note），不能散落各文档末尾无人跟踪。

**为什么**：待确认项散落各处、没有汇总、没有挂任务，形成不了闭环。

## 3. 执行步骤

### 步骤 1：立项 + 需求（合并）

**目的**：对齐做什么/不做什么/成功标准，并把定位变成可验证、带编号的功能清单。

> 按需加载检查清单（refs/）：需求-MRD.md / 需求-BRD.md / 需求-PRD.md / 需求-分析.md——只加载与当前需求类型相关的，逐项覆盖不漏。

```text
1. 追问关键决策（缺信息即问，禁止编造）：
   - 做什么（一句话定位）
   - 不做什么（边界）
   - 给谁用（目标用户）
   - 成功标准（什么算做成）
2. 梳理功能清单（每项）：功能描述 + 验收标准 + 优先级（高/中/低）
3. 逐条编号：每条需求/功能点给唯一 ID（REQ-xx / FR-xx）——铁律 1
4. 验收标准必须可测（能明确判断"完成/未完成"）
5. 需求条目在问题系统创建（type=requirement/feature）
6. 走评审：draft → review → confirmed（门禁）——铁律 2
7. 考虑全面：对照检查清单逐项覆盖，不漏维度（市场/用户/竞品/功能/非功能/风险）
8. 行业知识不足 → 调用 deep-research 补充（市场/竞品/技术趋势，有据可查）
```

**产出**：`docs/需求/00-功能清单.md`

```text
# 功能清单

## 定位与边界
- 定位：{一句话}
- 边界：{不做什么}
- 成功标准：{什么算做成}

## 功能清单

| 编号 | 功能 | 描述 | 验收标准 | 优先级 |
|------|------|------|---------|--------|
| REQ-01 | ... | ... | ... | 高 |
```

**门禁**：用户认可定位/边界/成功标准/功能清单，且所有需求条目 confirmed 后才进步骤 2。

### 步骤 2：分析（需求追踪矩阵）

**前置**：已有功能清单（步骤 1 产出）。

**目的**：建立需求 → 功能 → 模块的映射，识别关键流程与数据主线。

```text
1. 建需求追踪矩阵（RTM）：需求 ID → 功能 → 初步模块映射（铁律 1）
2. 识别关键流程与数据主线
3. 明确非功能需求（性能/并发/安全），未明确标「待补充」
```

**产出**：`docs/需求/01-需求追踪矩阵.md`（或并入功能清单）

**门禁**：每条需求都有对应的功能映射，无孤儿需求。

### 步骤 3：方案设计（详细文档）

**前置**：已有功能清单 + RTM（步骤 1/2 产出）；缺失则建议用户先完成，不自动补做。

**目的**：定架构，详细到可直接指导编码。

> 按需加载检查清单（refs/）：设计-概要.md / 设计-详细.md——重点覆盖模块间关系（架构图画 drawio）。

```text
1. 概要设计：模块划分 + 职责 + 依赖 + 接口/数据约定（收敛到约定层，铁律 4）
2. 技术选型：调研对比，标注依据（禁止引入未论证的技术栈）
3. 详细设计（按需拆分多份）：
   - 数据模型：建表 DDL、字段类型、索引、主键策略
   - 接口契约：字段级 OpenAPI 3.1 schema、请求/响应体、枚举、状态码
   - 关键流程：时序图 + 异常分支 + 状态机
4. 每份详细设计文档头部标注「关联」的上游文档与节（铁律 1）
5. 设计图：主流程、细分流程、状态机、架构部署（drawio）
6. UI 原型交 system-ui-design（概要出骨架线框、详细出高保真 HTML）
7. 关键决策点向用户确认
```

**产出**：

```text
docs/设计/01-概要设计说明书.md
docs/设计/02-详细设计-数据模型.md
docs/设计/03-详细设计-接口契约.md
docs/设计/04-详细设计-关键流程.md
docs/设计/*.drawio（主流程/细分流程/状态机/架构部署）
```

**门禁**：主键策略、字段命名、接口契约全系统一致，无矛盾；每份文档回指需求；用户确认方案后才进步骤 4。

### 步骤 4：任务分解

**前置**：已有设计文档（步骤 3 产出）。

**目的**：把确认的方案拆成可独立执行、可验证的开发任务。

```text
1. 拆任务：每个任务对应一个可独立编码/验证的单元
2. 排依赖：标注任务间依赖（铁律 3）
3. 定优先级 + 排期
4. 逐条登记进任务系统，关联对应需求与设计文档节
```

**产出**：已登记到任务系统的任务清单（编号、排期、依赖、状态以系统为准）。

> **登记动作归 `task-manager`**：工具与必填字段见其 §2（`create_task`），状态流转见 §3，调用失败的离线兜底见 §12。本技能不重抄字段清单——两处各写一份必然漂移。
> 本技能只管一件事：登记**之前**判断任务拆得够不够格（铁律 3），以及**登记时**带上「关联设计」回指。

**门禁**：每个任务可独立执行、可验证，且回指设计文档节；完成后交 `system-development` 执行。

---

## 关键约束

| 约束 | 说明 |
|------|------|
| 够用即止 | 决策记录写「决策+依据+验收标准」，不套完整模板、不写面子章节 |
| 门禁确认 | 步骤 1/3 经用户确认才继续（先规划后执行） |
| 证据优先 | 选型/接口/数据禁止编造，缺信息追问 |
| 可追溯 | 需求编号 + 设计回指 + RTM（铁律 1） |
| 阶段边界 | 概要只到约定层，字段级下沉详细设计（铁律 4） |
| 待确认集中 | 待确认项汇总一处 + 挂到任务备注（铁律 5） |
| 衔接下游 | 步骤 4 任务须标注「关联设计」节，供编码引用 |

## 输出

```text
docs/需求/00-功能清单.md（编号 + 验收标准）
docs/需求/01-需求追踪矩阵.md
docs/设计/（概要 + 详细设计 + drawio）
任务清单（经 `task-manager` 登记；字段与状态见其 §2/§3）
```
