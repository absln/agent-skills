# system-development

> 系统开发阶段的**编排入口**。本文件只定义四件事：阶段划分与门禁、技术栈探测规则、全阶段质量门槛、禁止事项。
> 各阶段详细工序在 `refs/` 下，**进入该阶段时才读，未进入不要预读**——预读会把下游阶段的指令提前塞进上下文，弱化阶段门禁。

## 前置条件

- 已确定角色为**开发**职责域
- 已加载项目 `README.md`（技术栈、构建命令）
- 已了解项目设计文档和开发任务
- 命名：语言社区通行风格（Python snake_case / C# PascalCase / Rust snake_case），同仓库内一致优先于任何外部规范
- 注释：只写「为什么」，不写「做了什么」；公开 API 必须有 docstring/文档注释，含参数、返回值、抛出异常
- 错误处理：不吞异常；错误分层（可恢复用 Result/返回值，不可恢复才抛）；每层转换时保留原因链
- 依赖：新增依赖须声明版本并说明理由；能用手写 20 行解决的不引三方包

## 阶段划分与门禁

开发是**时间序列**，阶段之间有门禁。按当前所处阶段读取对应指令：

| 阶段 | 步骤 | 出口门禁（必须满足才进下一阶段） | 指令 |
|---|---|---|---|
| 计划 | 1 获取任务<br>2 读设计 + 出方案 | **实现方案经用户确认** | `refs/stage-plan.md` |
| 编码 | 3 编码<br>4 单元测试 | 单测全绿 + 逐条对照验收标准 | `refs/stage-code.md` |
| 交付 | 5 集成验证<br>6 部署<br>7 更新任务 + 提交 | 端到端通过 + 回归无损 + 任务已完结 | `refs/stage-ship.md` |

门禁是硬约束：上一阶段门禁未过，不得读取下一阶段指令。

## 规范加载规则

三类判定的**依据不同**，必须分开判断，不要合并成一张「探测」表：

### 一、常驻红线（无条件遵守）

与任务无关，任何开发任务都不得违反。漏读的代价是返工，不是省 token：

| 技能 | 为什么常驻 |
|---|---|
| `http-api-standards` | 信封 / 错误体 / 分页 / 状态码是跨端契约，改错要前后端一起返工 |
| `database-standards` | 字段类型 / 枚举 / 索引一旦落库难回改 |

### 二、技术栈探测（客观仓库事实）

用**文件系统事实**判定，不靠对话里提到的词猜：

| 探测信号 | 加载 |
|---|---|
| `pyproject.toml` / `requirements.txt` 存在 | `backend-python-standards` |
| `Cargo.toml` 存在 | `backend-rust-standards` |
| `package.json` 存在且依赖含 `vue` | `frontend-standards` |

多个命中则全部加载。**落地次序**：数据层 → 契约层 → 实现层；次序不改变强制力。

### 三、文档产出（任务性质）

编写或修改设计文档时，一律以 `system-design` 为准——文档结构、需求编号、设计回指、阶段边界都归它管，**不要另起一套格式**：

| 触发 | 加载 |
|---|---|
| 需编写 / 修改 `docs/设计/` 下方案、需求或任务清单 | `system-design` |
| 编码反馈要回写设计文档 | `system-design`（按铁律 1 保持回指不断链） |

GJB 国军标交付文档（`docs-generate-china-standard`）**不属于本阶段的编排范围**，仅当用户明确要求国军标交付物时单独点名加载。图表与办公文档（`drawio-skill`、`docx-generation`、`pptx-generation`）同理，按需点名。

## 质量门槛（全阶段适用）

### 定性标准

- [ ] 功能完整：覆盖任务验收标准
- [ ] 异常覆盖：正常路径 + 输入校验 + 异常分支
- [ ] 单测覆盖：核心逻辑有对应测试
- [ ] 集成通过：端到端核心流程跑通
- [ ] 命名规范：符合研发规范
- [ ] 无硬编码：密钥/路径/配置从环境或配置读取
- [ ] 无死代码：无注释掉的代码、未用导入
- [ ] 依赖清洁：新依赖已声明版本

### 量化指标

| 维度 | 指标 | 标准 |
|------|------|------|
| 完整性 | 功能覆盖率 | ≥90% |
| | 测试通过率 | 100% |
| 正确性 | 静态检查 | 零致命/严重告警 |
| 可维护性 | 单函数圈复杂度 | ≤15 |
| | 单函数行数 | ≤50 |
| 安全性 | 硬编码密钥 | 零 |
| 规范性 | 命名规范符合率 | ≥95% |

## 输出

- 实现方案（计划阶段）
- 代码 + 单元测试（编码阶段）
- 集成验证结果 + 部署产物（交付阶段）
- 任务状态更新（操作方式见 `task-manager` §3）与提交记录

## 禁止事项

| 禁止 | 说明 |
|------|------|
| 编造 API | 编写设计文档未定义的接口 |
| 忽略错误 | IO/外部调用不写错误处理 |
| 硬编码密钥 | 密码/Token/连接串写死在代码 |
| 跳过方案 | 未经确认就编码 |
| 跳过单测 | 核心逻辑无测试就提交 |
| 跳过集成 | 只跑单测不做端到端 |
| 擅自猜测 | 不确定业务逻辑不询问就假设 |
| 过度设计 | 为不需要的场景提前加抽象 |
| 预读下游阶段 | 未过门禁就读下一阶段指令 |
