# 绩效与问题溯源（RTM）

> task-manager 技能的素材库。主文件 `SKILL.md` §9 / §10 保留触发条件与硬性规则（红线），
> 取数口径、写入坐标、生成步骤、自检清单在此。

## 生成绩效
#### 9.1 区间与文件

```
季度区间（左闭右开，按 done_at 取数）
  Q1 = {年}-01-01 → {年}-04-01
  Q2 = {年}-04-01 → {年}-07-01
  Q3 = {年}-07-01 → {年}-10-01
  Q4 = {年}-10-01 → {年+1}-01-01

模板：绩效/绩效考核-{季末月}01-{姓名}.xlsx
  季末月 = Q1→03、Q2→06、Q3→09、Q4→12（文件名里的月份是季末月，不是季度首月）
  例：2026 Q4 → 绩效/绩效考核-202612-{姓名}.xlsx
```

- 模板缺失时**不要自己造表**：从 `绩效/` 下取最近一份同期模板 `shutil.copy` 后改名，并告知用户「模板为复制件，请确认权重」。
- 已有同名文件时**先问是否覆盖**，不静默改写。

#### 9.2 六个考核项的取数口径

| 序号 | 考核项 | 取数来源 | 归集规则 |
|---|---|---|---|
| 1 | 方案设计 | `task_type=design` 且 `status=done` | 按 `done_at` 落季度；标题含「方案/设计/论证」的归此项 |
| 2 | 软件开发 | `task_type` 以 `software` 开头 | 按子类分：`software.code` 功能完成度、`software.test` 代码质量佐证、`software.analysis` 设计说明 |
| 3 | 工作汇报 | 周报文件 `周报/{年}/研发周报-*.xlsx` | 数本季度周报份数、缺交周次（周五 21:00 截止） |
| 4 | 知识产权 | `task_type=ip` | 专利/软著交底书按标题计数（如「交底书」） |
| 5 | 团队协作 | 无系统数据 | **留空并标注「无系统数据，需人工填写」**，不推断 |
| 6 | 考勤 | 无系统数据 | 同上，不推断 |

> 取数：`list_tasks(status="done", done_from=<季度首日>, done_to=<下一季度首日>, assignee_id=<本人>)`；按人筛时传 `assignee_id`（先用 `list_users` 查）。

#### 9.3 写入规则（`季度绩效考核` sheet，A1:L19）

| 列 | 内容 | 谁写 |
|---|---|---|
| A | 序号（1–6，模板已有） | 不动 |
| B | 考核项目（模板已有） | 不动 |
| C / D | 自评 / 综评 **分数** | **禁止写**（人填） |
| E | 考核说明：本季该项目的**事实描述** | Agent 写 |
| F | 补充事实（如知识分享、专利撰写条数） | Agent 写（有则写） |
| G–J | 子项得分 | **禁止写** |
| K | 权重 | 不动（以当季模板为准，权重会在 0.4/0.6 与 0.6/0.4 间切换，不照抄示例） |
| L | 说明 | 有则写 |

E 列写法（每项 2–4 条，带 task id 便于追溯）：

```
本季完成方案设计任务 3 项（#12 架构方案、#19 详细设计、#24 接口设计），均按期提交。
软件开发完成 8 项（#31–#38），其中 2 项延期，原因见周报 2026W42。
```


## 绩效生成后校验（7 条）

#### 9.5 校验（7 条）

1. C/D/G–J 全部为空 → 通过；有任何 Agent 写入的分数 → 回滚。
2. E 列 6 项都有内容或明确标注「无系统数据」。
3. 每条事实能追到 task id 或周报文件。
4. 任务 `done_at` 全部落在本季度区间内。
5. 合计行公式未被改写（`data_only=False` 读回仍是公式）。
6. 权重 K 列与模板一致（未被覆盖）。
7. 文件名月份 = 季末月（Q4 → 12）。

## 问题溯源与变更影响（RTM）

#### 10.1 结构

```
需求树（issues 表，parent_id 组树）
  requirement（需求）
    └ feature（功能）
        ├ test_case（用例）
        └ bug（缺陷，不能作父）

任务 ↔ 问题：task.refs = [issue_id, ...]
任务 ↔ 任务：task.predecessors = [task_id, ...]（前置依赖）
```

#### 10.2 生成需求追踪矩阵（RTM）

```
1. list_issues(project_id=X, parent_id=0, type=requirement) → 拿全部顶层需求
2. 对每个需求：list_issues(parent_id=<需求id>) → 子功能
3. list_tasks(project_id=X, limit=200) 分页拉全量 → 建 refs 反查索引 {issue_id: [task...]}
4. 逐需求判定覆盖状态（见下表）
5. 输出 RTM 表
```

| 判定 | 条件 |
|---|---|
| ✅ 已覆盖 | 有 test_case 且其关联任务全部 `done` |
| 🟡 进行中 | 有任务但存在 `todo/in_progress/blocked` |
| ⚠️ 仅用例无任务 | 有 test_case 但无任务 `refs` 指向 |
| ❌ 无任务 | 需求/功能下既无用例也无任务 |
| 🔴 Bug 未闭环 | 存在 `status != closed` 的 bug |

输出表：

| 需求 | 功能 | 用例数 | 关联任务 | 完成 | 状态 | 证据 |
|---|---|---|---|---|---|---|
| #3 任务管理 | 登记 | 2 | #29,#30 | 2/2 | ✅ | task#29 done_at=… |

> **存量宽限**：`refs` 绑定只对**新建任务**强制；存量任务无 `refs` 不算缺陷，在下次变更时补挂。RTM 里存量缺失记为「未绑定（存量）」，不计入 ❌。

#### 10.3 变更影响分析

```
1. 定位变更对象：issue_id（需求/功能）或 task_id
2. 向下找子问题：list_issues(parent_id=<id>) 递归到叶子
3. 反查任务：所有 refs 命中上述 issue 集合的任务（含 done）
4. 顺依赖扩散：对命中任务，用 get_task 取 successors，递归收集后继任务
5. 输出影响清单
```

输出表：

| 层 | 对象 | id | 状态 | 影响说明 |
|---|---|---|---|---|
| 需求 | 任务管理 | #3 | confirmed | 变更源 |
| 任务 | 登记接口改造 | #29 | done | 已实现，需回归 |
| 任务 | 登记页 UI | #33 | in_progress | 需调整 |
| 缺陷 | 登记重复校验失效 | #7 | fixing | 需重验 |
